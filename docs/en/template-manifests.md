# Template manifests

Every starter includes a `template.manifest.json` at its root. The CLI
discovers these files in the directories directly under `templates/backend/`
and `templates/frontend/`. The identifier comes from the manifest, not from the
folder name or the package manager file.

The JSON format lets you read the metadata without installing the starter's
dependencies. The current schema is `1`, described in
[`template-manifest.schema.json`](../template-manifest.schema.json). From the
root, run `npm run validate:templates` to validate templates and extensions.

## Fields

| Field | Meaning |
| --- | --- |
| `schemaVersion` | Format version; currently `1`. |
| `id` | Stable `<kind>:<slug>` identifier, for example `backend:fastapi`. |
| `version` | Semantic version of the contract of the project generated by the template. |
| `kind` | `backend` or `frontend`; matches the `id` prefix. |
| `displayName`, `description` | Name and description of the template. |
| `runtime` | `language`, `packageManager` and, optionally, `version`. |
| `capabilities` | Unique list of implemented capabilities, such as `auth.password`. |
| `environment.required` | Variables the application must configure; each entry contains `name`, `secret` and `description`, without values or credentials. |
| `development` | Local port and URL (`port`, `baseUrl`). The schema allows it as optional, but the CLI requires `baseUrl` for backends. |
| `compatibility` | Optional field with `requiresBackendCapabilities`, used when combining frontend and backend. |

`secret` flags sensitive variables; it does not set their value or replace the
deployment's secret management. Capabilities describe implemented behaviour,
not future plans. A template that only has billing models must not declare
`billing.stripe` without the matching integration.

## Catalog and selection

Full IDs are used in extension manifests. The `--backend` and `--frontend`
flags accept the short name, without the prefix:

| Type | ID | CLI selector | Template version |
| --- | --- | --- | --- |
| Backend | `backend:fastapi` | `fastapi` | `0.1.0` |
| Backend | `backend:nestjs` | `nestjs` | `0.1.0` |
| Backend | `backend:fastify` | `fastify` | `0.1.0` |
| Frontend | `frontend:nextjs` | `nextjs` | `0.1.0` |
| Frontend | `frontend:react-router` | `react-router` | `0.1.0` |
| Frontend | `frontend:astro` | `astro` | `0.2.0` |

From a checkout, check the catalog and the help with:

```sh
node packages/cli/bin/create-my-saas.js --list
node packages/cli/bin/create-my-saas.js --help
node packages/cli/bin/create-my-saas.js my-saas --backend fastapi --frontend nextjs
```

Template versions are independent of the CLI package version. Generation
requires at least `--backend` or `--frontend` and a destination that does not
exist. It also accepts a single template; screens that need an API require a
configured backend to work.

## Browser sessions and compatibility

All three frontends, including Astro, declare `auth.browser-sessions` and
include `API_PROXY_TARGET` in `.env.example`. When generating frontend and
backend together, the CLI replaces that value with the backend's
`development.baseUrl` when the frontend declares capability requirements.
Next.js and React Router include API proxies; Astro includes a development
proxy with `API_PROXY_TARGET` and uses `PUBLIC_API_BASE_URL` or the
same-origin gateway in production.

The CLI checks `compatibility.requiresBackendCapabilities` before writing the
project. FastAPI and NestJS are compatible with all three frontends; Fastify
only with Astro. Next.js and React Router require `organizations` and
`billing.stripe`, which Fastify does not implement. Choosing the `individual`
model does not remove these requirements. See [product models](./product-models.md).

Base Astro includes authentication, a private area and administration, but the
billing interface requires `--feature billing`. That alias maps to
`community:astro-billing`, compatible with Astro and FastAPI or NestJS. See
[extension manifests](./extension-manifests.md).

## Adding a template

1. Add the starter to `templates/backend/` or `templates/frontend/`.
2. Create its `template.manifest.json` with a stable ID and the matching
   `kind`.
3. Declare only implemented and tested capabilities; reuse the existing names
   when they mean the same thing.
4. Declare the required variables in `environment.required` and document their
   values in `.env.example`, without real credentials.
5. Add `development` for a backend and the compatibility requirements for a
   frontend that uses an API. Run `npm run validate:templates` and add tests
   for generation and for the compatible combinations.

## Catalog and compatibility

| Layer | Option | Status and purpose |
| --- | --- | --- |
| Backend | `fastapi` | Full Python API: browser sessions, CSRF, users, organizations, RBAC, audit log, recovery/verification, OAuth and billing. |
| Backend | `nestjs` | Modular TypeScript API with the same functional contract as FastAPI. |
| Backend | `fastify` | Lightweight TypeScript API with PostgreSQL, sessions, CSRF, recovery, email verification and Google/GitHub OAuth. It does not include organizations or Stripe Billing yet. |
| Frontend | `nextjs` | Dashboard with browser sessions, protected routes and account flows. |
| Frontend | `react-router` | React dashboard with Framework Mode rendering, protected routes and a same-origin API proxy. |
| Frontend | `astro` | Fast marketing, docs and blog site, with a light authenticated area compatible with all three backends. Per-organization billing is optional. |

Each starter's capabilities are declared in its `template.manifest.json`. The
CLI compares them before writing files: dashboards that require organizations
and Stripe Billing need FastAPI or NestJS. Fastify can be generated alone or
with light Astro, because it covers the session, recovery, verification and
OAuth contract of that authenticated area. To add billing to Astro, select
`--feature billing` explicitly; the CLI limits it to FastAPI and NestJS.
